---

## はじめに

「AIがコードを書いてくれる時代に、エンジニアは何をすればいいのか？」

この問いに向き合うために、私は仕様駆動開発という考え方を調査しました。
単なるトレンドの紹介ではなく、**自分たちの開発現場がどう変わっていくのか**という視点で整理しています。

---

## 仕様駆動開発とは？

仕様駆動開発（Spec-Driven Development / SDD）とは、**コードより先に「仕様」を丁寧に書き、それをもとに開発を進めるアプローチ**です。

「仕様書を先に書く」こと自体は昔からある考え方ですが、AIが登場したことで意味合いが大きく変わりました。

以前の仕様書は「人間が読むためのドキュメント」でした。
しかし今は、**AIへの指示書（プロンプト）としても機能する**ようになっています。

つまり仕様さえしっかり書ければ、AIが実装まで担ってくれる。
そのような開発フローが、現実のものになってきています。

---

## 従来の開発との比較

| | 従来の開発 | 仕様駆動開発（AI活用） |
|---|---|---|
| **主な成果物** | コード | 仕様書 ＋ コード |
| **実装者** | 人間 | AI（人間がレビュー） |
| **仕様の役割** | 参考資料 | AIへの入力 ＝ 設計の核 |
| **修正コスト** | 後工程ほど高い | 仕様段階で修正できる |
| **必要なスキル** | 実装力 | 要件定義・仕様の言語化力 |

従来の開発では「なんとなく仕様が決まっていたらコーディングを始める」ことも多くありました。
しかし仕様駆動開発では、**曖昧なまま先に進めない**ことが逆に強みになります。
AIは曖昧な指示が苦手なため、「仕様を明確にする」プロセスが自然と強制されるのです。

また、近年「バイブコーディング（Vibe Coding）」という言葉も広まっています。
これはAIとの会話を通じてノリで実装を進めるスタイルですが、チャット履歴に決定事項が埋もれてしまい、後から「何をどう作ったか」がわからなくなる問題があります。
仕様駆動開発はこの課題を解決するアプローチとして、特に注目されています。

---

## 調査したツール：Kiro・SpecKit・OpenSpec

今回の調査では、仕様駆動開発を実践するための具体的なツールを3つ詳しく調べました。
それぞれ思想や特徴が異なるため、チームの状況に応じた使い分けが鍵になります。

---

### 1. Kiro（AWS製）― IDE一体型の本格派

**Kiro**は、AWS（Amazon）が2025年夏にリリースしたAI搭載のIDE（コードエディタ）です。
VS Codeをベースに作られており、**仕様駆動開発をIDE本体に組み込んでいる**のが最大の特徴です。

#### 開発フロー

```
自然言語で要件を入力
    ↓
要件定義書（EARS記法のユーザーストーリー + 受け入れ条件）を自動生成
    ↓
技術設計書（アーキテクチャ・データベース設計・APIなど）を生成
    ↓
タスクリスト（依存関係順に並んだ実装ステップ）を生成
    ↓
AIエージェントが実装を実行
```

自然言語で「こういうものを作りたい」と伝えるだけで、
要件定義 → 設計 → タスク分解 → 実装 という流れを一貫して支援してくれます。

#### 特徴的な機能

**Hooksという仕組みが面白い。**
ファイルを保存したとき、コンポーネントを修正したときなど、**特定のイベントをトリガーにしてAIエージェントが自動で動く**仕組みです。
たとえば「ReactコンポーネントをSaveしたら、テストを自動更新する」といった設定ができます。

また、**仕様書とコードが常に同期される**設計になっており、実装が進んでも仕様書が陳腐化しにくい構造になっています。

#### 実績と課題

1,500人以上のエンジニアが実際に使っており、仕様作成が「数週間から数時間」に短縮されたという事例もあります。
一方で、「小さなツールを作るだけなのに仕様を書くのが重い」という声もあり、**規模や用途によって向き不向きがある**のが正直なところです。

---

### 2. GitHub Spec Kit（GitHub製）― OSS・エージェント横断の標準化ツール

**GitHub Spec Kit**は、GitHubが2025年9月にオープンソースで公開したツールキットです。
特定のIDEに縛られず、**Claude Code・GitHub Copilot・Cursor・Gemini CLIなど20以上のAIエージェントに対応**しているのが強みです。

#### 開発フロー（コマンド一覧）

```
/speckit.constitution  ← プロジェクトの設計原則・コーディング規約を定義
/speckit.specify       ← 何を作るかを記述（ユーザーストーリー・受け入れ条件を生成）
/speckit.plan          ← 技術スタック・アーキテクチャを決定（実装計画を生成）
/speckit.tasks         ← 実装タスクリストを生成
/speckit.implement     ← タスクを実行してコードを生成
```

注目すべきは**「Constitution（憲法）」**の概念です。
プロジェクトの「テスト方針」「コーディング規約」「使用禁止ライブラリ」などをmarkdownで定義しておくことで、AIが常にその原則に従って開発を進めます。
チームの暗黙知を明文化し、AIに学習させるようなイメージです。

#### 特徴と注意点

リリース1週間で1.6万スター超を獲得するほど注目を集めていますが、
開発者自身が「これは実験的なプロジェクトです」と強調しており、**現時点ではプロダクション用途より学習・試験的な利用が向いています。**
また設定手順が多く、Pythonの環境構築が必要なため「重い」と感じる声もあります。

---

### 3. OpenSpec（OSS）― 軽量・既存プロジェクト向けの現実解

**OpenSpec**は、Fission-AIによって開発されたオープンソースのSDDフレームワークです。
Kiro・SpecKitと比較したとき、最もシンプルで導入しやすいのが特徴です。

#### 特徴

**「Brownfield-first（既存プロジェクト対応）」**を明確に掲げています。
KiroやSpecKitは新規プロジェクト（0→1）を前提に設計されていますが、
OpenSpecは**すでに動いているプロダクトに対して仕様を追加・管理することを得意**としています。

インストールはnpmで5分以内に完了し、以下3つのコマンドだけで基本的なフローが回ります：

```
/opsx:new      ← 新しい変更の仕様フォルダを作成
/opsx:ff       ← proposal.md / specs / design.md / tasks.md を自動生成
/opsx:apply    ← タスクに沿ってAIが実装を実行
/opsx:archive  ← 完了した仕様を「確定済み仕様」としてアーカイブ
```

#### アーカイブの考え方が面白い

OpenSpecには「仕様のアーカイブ」という概念があります。
変更中の仕様は `openspec/changes/` に置かれ、実装が完了したら `openspec/specs/` に移動します。
これにより、「今のコードが何をするものか」が常に仕様として残り続けます。
**コードの意図が消えない**という点で、特にチーム開発や引き継ぎの場面で効果を発揮します。

## 3ツールの比較まとめ

| | Kiro | GitHub SpecKit | OpenSpec |
|---|---|---|---|
| **提供元** | AWS（Amazon） | GitHub（Microsoft） | OSS（Fission-AI） |
| **形態** | IDE（VS Codeベース） | CLIツール + テンプレート | CLIツール |
| **対応AIモデル** | 主にClaude | 20以上のAI対応 | 20以上のAI対応 |
| **新規 / 既存** | 新規向け | 新規向け | 既存プロジェクト向け◎ |
| **導入のしやすさ** | やや重い（IDEのインストール） | やや重い（Pythonが必要） | 軽い（npm install） |
| **成熟度** | 商用・実績あり | 実験的 | 急速に成長中 |
| **向いているチーム** | AWS環境・本格的なSDD導入 | マルチAIツール環境 | スモールスタート・既存改修 |
